- 主题：**公开的** AI 安全与滥用防范新闻。分析师语气。
- **2026-09-27 改版**：深化漏洞、提示词注入（prompt injection）、越狱（jailbreak）研究、安全研究者与相关组织动态、厂商回应和修复状态。本刊负责这些事件的**技术分析**；双语每日新闻「AI 安全观察」只写短讯，本刊已有完整报道时它会链接过来。
- **2026-09-30 扩充**：新增「技术解析」板块，讲清各类攻击方法（越狱、提示词注入等）**为什么对大模型有效、影响什么、如何防范**；防御内容扩充为「防御与缓解」。

## 关键范围限制（硬性）

可以写：漏洞与提示词注入的披露、越狱研究的**存在和影响**、攻击类别的**原理层面解释**（见下文「技术解析」）、研究者与组织的公开发布、厂商回应和修复状态、政策、厂商风险框架（preparedness frameworks）、防御方法与工具、负责任披露（responsible disclosure）。每条只写「谁、何时、影响什么产品或场景、厂商如何回应、目前修复状态」。

**不得**包含越狱提示词、攻击载荷、提示词模板或片段、编码后的攻击字符串、漏洞利用步骤、针对某个产品的绕过方法，或来自越狱社区的操作教程；引用研究时只写结论、原理类别和影响，不复述可复现的方法。拿不准某句话会不会帮人复现攻击时，删掉它。

每条在 summary 开头标明**证据等级**，三选一：

- 【研究演示】研究者或红队在受控环境中演示，尚无实际受害记录；
- 【已确认漏洞】厂商或权威机构确认存在，写明是否已修复；
- 【已发现实际利用】已有真实攻击或受害案例，写明范围和出处。

不涉及具体漏洞或攻击的条目（`防御与缓解`、`政策监管`、`厂商框架`，以及只谈组织动态的 `研究者与组织`）标【证据等级：不适用】，修复状态也写「不适用」。（2026-10-01 用户确认）

并写明**修复状态**：已修复 / 修复中 / 厂商未回应 / 不适用。

## 技术解析（每期必出 1 条）

用公开论文和厂商技术报告，讲清一类攻击或防御技术。本周有相关新研究就讲本周的；没有就从近 12 个月或经典研究中选一个本刊还没讲过的主题（在报告中说明）。可选主题举例：多轮渐进式越狱、长上下文多样本越狱、对抗性后缀、间接提示词注入（藏在网页、邮件、文档里的指令）、智能体与工具调用被劫持、训练数据投毒与后门、系统提示词泄露、模型窃取与提取、多模态（图片、音频）注入。

`summary` 按顺序写：

1. **是什么**：一句话定义，并写明出处（论文或厂商报告、机构、发表时间）。
2. **为什么对大模型有效**：只讲原理类别，如「利用模型对上下文示例的模仿倾向」「模型分不清数据和指令」，**不给任何可照做的写法、模板或步骤**。
3. **影响与证据等级**：影响哪些产品或场景（聊天助手、智能体、企业知识库等），证据等级按下文三选一。
4. **如何防范**：至少 3 条具体措施，分对象写——开发者（如输入输出过滤、把外部内容与指令隔离、工具权限最小化、敏感操作人工确认）、企业（如红队评测、日志审计、供应商安全评估）、普通用户（如不让智能体自动处理来路不明的文件和网页、不授予不必要的权限）。
5. **厂商现状**：主要厂商公开的缓解措施和效果（写明出处）；没有公开信息就写「未见公开说明」。

## 条目安排

- 共 4–9 条，不凑数。`category`：`技术解析` / `漏洞与提示词注入` / `越狱研究` / `研究者与组织` / `厂商回应与修复` / `政策监管` / `厂商框架` / `防御与缓解`。
- `防御与缓解`：新的防御方法、评测基准、开源防御工具和最佳实践，写清适用场景与局限。
- **每期都有监测结论**：`lead` 的 `summary` 以「本周监测结论：」开头，用一两句话概括本周全局，并逐项说明漏洞、提示词注入、越狱研究、厂商修复四类中**哪几类本周没有可信新动态**（直接写「本周无可信新披露」，不编造更新）。
- 四类都没有可信新动态、政策与框架也无新进展时，仍出「技术解析」：此时技术解析兼作头条，`summary` 先写「本周监测结论：本周无可信新动态……」，再接技术解析正文。
- `important` 2 条。
- 英文来源填 `originalTitle`，头条尽量附 2 个以上来源，让原标题在来源面板中显示（规则见 README 第 4 节）。
